## 1. 产品概述

### 1.1 产品背景

餐饮行业正经历从"经验经营"向"数据经营"的转型。传统餐厅普遍存在以下痛点：

- 点餐依赖人工，高峰期服务员忙不过来，翻台效率低；
- 顾客到店排队久、体验差，缺少提前预约与取号手段；
- 堂食、外卖两套体系割裂，订单、菜品、库存、会员数据分散；
- 多门店连锁缺乏统一管控，总店无法实时掌握各店经营数据；
- 会员、优惠券、积分等营销手段依赖人工记录，无法沉淀数字资产。

### 1.2 产品定义

**智慧餐厅** 是一套面向餐饮企业的"三端一体"数字化经营管理平台：

| 端 | 载体 | 目标用户 | 核心价值 |
|---|---|---|---|
| 客户端 | 微信小程序 | C端顾客 | 扫码点餐、外卖点餐、排队取号、预约订座、会员钱包 |
| 员工端 | APP | 服务员/收银/后厨 | 点餐开台、叫号、后厨出单、收银结账、会员充值 |
| 商户端 | Web管理后台 | 店长/总店长 | 门店、菜品、库存、订单、会员、促销、报表全量管理 |

### 1.3 产品愿景

让每一家餐厅"一部手机管店、一块屏幕经营、一套数据决策"，实现顾客自助化、员工数字化、管理数据化。

## 2. 产品定位与目标

### 2.1 产品定位

面向中小型连锁餐饮企业的 **轻量化 SaaS 智慧餐饮解决方案**，以"点餐—支付—经营"闭环为核心，从单店工具逐步演进为连锁管控平台。

### 2.2 产品目标

1. **提效**：顾客自助点餐占比 ≥ 60%，服务员人均服务台数提升 50%，收银耗时降低至 30 秒内；
2. **增收**：外卖+堂食双渠道增长，会员复购率提升 20%，客单价提升 10%；
3. **降本**：后厨按单出菜、库存预警，食材损耗率下降 15%；
4. **管控**：总店可实时查看所有门店的订单、销售、库存与员工数据，形成统一决策视图。

## 4. 市场与竞争分析

### 4.1 市场机会

中国餐饮市场规模庞大，连锁化率持续提升，中小餐饮商户对"低成本、易上手"的数字化工具需求旺盛。微信小程序天然的流量入口与扫码能力，使"轻工具 + 高触达"的智慧餐饮模式具备明显获客优势。

### 4.2 竞品对比

| 维度 | 智慧餐厅（本项目） | 传统SaaS餐饮系统 | 平台型外卖工具 |
|---|---|---|---|
| 部署成本 | 轻量，按门店订阅 | 较重，需硬件与实施 | 佣金抽成较高 |
| 数据自主 | 全量自有数据，可出报表 | 数据归商户 | 数据在平台侧 |
| 三端覆盖 | 客户+员工+商户全链路 | 侧重商户侧 | 侧重C端交易 |
| 差异化 | 连锁多店管控 + 会员钱包 | 单店功能深 | 流量大但受平台约束 |

### 4.3 差异化策略

1. **连锁管控**：总店长视角统一管理多门店，会员类别/小票/硬件全国统一，与单店工具形成差异；
2. **会员资产私有化**：钱包、红包、积分、优惠券全部沉淀在自有体系，不依赖外卖平台；
3. **三端数据打通**：堂食、外卖、自取三种订单形态统一建模，报表口径一致。

┌──────────────────────────┴──────────────────────────────┐
│                      接入层 / 网关                        │
│      认证鉴权(JWT)  限流  日志  微信/支付宝支付回调           │
└──────────────────────────┬──────────────────────────────┘
┌──────────────────────────┴──────────────────────────────┐
│                     业务服务层                            │
│   用户/门店  菜品/库存  订单/支付  会员/钱包  促销/积分  报表 │

### 6.2 关键技术选型建议

| 层 | 建议 | 说明 |
|---|---|---|
| 客户端 | 微信小程序原生 / uni-app | 一套代码多端发布 |
| 员工端 | uni-app / Flutter | 支持 iOS & Android |
| 商户端 | Vue3 + Element Plus | 中后台管理 |
| 服务端 | Spring Boot / Node.js(Nest) | 前后端分离，RESTful |
| 数据库 | MySQL 8.0 | 本规划配套建表脚本 |
| 缓存 | Redis | 排队叫号、购物车、会话 |
| 文件 | 对象存储(OSS) | 菜品图、评价图、头像 |
| 支付 | 微信支付、支付宝 | 服务端统一下单+回调 |
| 部署 | Docker + Nginx | 容器化，便于多店扩展 |

### 6.3 核心业务流程

- **外卖点餐**：选店 → 选菜 → 购物车 → 确认订单（选地址/自取、用券）→ 支付 → 门店接单 → 制作 → 配送/自取 → 完成 → 评价/积分；
- **堂食点餐**：扫桌码 → 选菜 → 下单 → 制作 → 收银结账（打折/优惠/免单/抹零）→ 支付 → 完成；
- **排队取号**：选桌型取号 → 排队列表 → 叫号 → 就位开台 → 关联堂食订单；
- **收银结账**：预结账列表 → 订单详情 → 结账方式（微信/支付宝/会员余额/扫码）→ 出账。

### 6.4 接口设计规范

| 规范项 | 约定 |
|---|---|
| 风格 | RESTful，资源名复数（`/api/v1/orders`、`/api/v1/dishes/{id}`） |
| 版本 | URL 前缀 `/api/v1` 管理，兼容旧版本 |
| 鉴权 | 客户端/员工端 JWT（Access Token 2h + Refresh Token 14d）；商户端 Web 会话 + 细粒度 RBAC（复用 `sys_permission`） |
| 统一返回 | `{ "code": 0, "message": "ok", "data": {...} }`，业务错误码分段：1xxx 参数、2xxx 业务、3xxx 权限、4xxx 支付、5xxx 系统 |
| 分页 | `page`/`size` 入参，返回 `{ "total", "pages", "list" }`，禁止全量拉取 |
| 幂等 | 下单/支付/退款等写接口必须传 `idempotency_key`（或客户端订单号），服务端唯一约束去重 |
| 安全 | 全链路 HTTPS；敏感字段（手机号/身份证/银行卡）返回脱敏；金额一律分单位整数或 DECIMAL 传输 |

### 6.5 幂等与并发控制

- **订单状态乐观锁**：`orders.version` 版本号，状态流转（接单/制作/结账/退款）以 `UPDATE ... SET version=version+1 WHERE id=? AND version=?` 判定，避免客户端重复提交或并发覆盖；零行受影响即冲突，回滚并提示刷新；
- **支付幂等键**：`payment_record.idempotency_key` 唯一约束，支付回调重试/重复通知只落一次账、只更新一次订单状态；
- **库存防超卖**：扣减使用 `UPDATE dish_stock SET stock=stock-? WHERE dish_id=? AND stock>=?` 条件更新，行数=0 视为库存不足；外卖配送超时补偿等异步任务用 Redis 分布式锁（SETNX + 过期时间）防止重复执行；
- **排队叫号并发**：`queue.call_count` 记录叫号次数，叫号/过号操作以状态条件更新保证幂等。

### 6.6 支付与对账

| 环节 | 方案 |
|---|---|
| 支付渠道 | 微信支付（JSAPI 小程序）+ 支付宝（APP/扫码），官方 SDK，仅后端持有密钥 |
| 回调 | 验签 → 幂等键去重 → 落支付流水 → 更新订单 → 通知出单/配送；失败重试至多 5 次，最终不一致由对账兜底 |
| 对账任务 | 每日 02:00 拉取渠道对账单与本地 `payment_record` 逐笔比对，异常（本地有渠道无/渠道有本地无/金额不一致）进 `对账差异表` 并告警 |
| 退款 | 走 `refund` 表留痕，原路退回，退款金额与 `order_detail.refund_amount` 联动，防止超额退 |
| 会员资金 | 余额/积分/红包流水强制记账（`member_balance_record` 等），人工调账必须留审计字段 |

### 6.7 安全与合规

1. **传输与存储**：全站 HTTPS/TLS1.2+；密码 bcrypt/scrypt 加盐哈希（严禁明文与裸 MD5，演示数据除外）；身份证、银行卡号 AES-256 加密存储、展示脱敏；
2. **访问控制**：JWT 无状态鉴权 + RBAC 权限点（`sys_role_permission` 控制菜单与接口）；员工敏感操作（结账/退款/改价）二次校验；
3. **输入与注入防护**：服务端参数校验（白名单/长度/类型）、预编译 SQL 防注入、XSS/CSRF 防护、接口限流（防薅羊毛）；
4. **日志与审计**：`staff_login_log`、`order_status_log` 完整留痕，操作日志保留 ≥ 180 天；
5. **合规**：遵守《个人信息保护法》（最小必要收集、脱敏展示、删除权）与支付相关监管要求，隐私政策与用户协议随小程序提审一并提供。

### 6.8 部署架构与高可用

| 层 | 方案 |
|---|---|
| 接入层 | Nginx 反向代理 + HTTPS 证书 + 静态资源 CDN |
| 应用层 | 后端集群（≥2 节点）无状态化，前端小程序/APP/Web 打包托管 |
| 数据层 | MySQL 主从 + 读写分离（读从库走报表查询），Redis 缓存菜品/台桌/会话/限流 |
| 对象存储 | 阿里云 OSS/腾讯 COS 存菜品图、评价图、营业执照 |
| 监控 | Prometheus + Grafana（QPS/耗时/错误率）、日志平台、支付告警、对账失败告警 |
| 备份 | 每日全备 + binlog 增量，跨机房冷备，定期演练恢复 |

### 6.9 扩展性规划

- **订单库拆分**：订单类表按 `store_id` 或月份分库分表（订单量 > 100 万/月时启用），报表走数仓/OLAP 而不直查业务库；
- **异步化**：下单/出单/短信通知走 MQ（RocketMQ/Kafka）削峰，出单推送给后厨端；
- **多门店弹性**：`store_id` 维度隔离 + 总店长跨店视角，新门店仅需初始化 `store` + `dining_table` + `printer`，1 周内可上线。

### 7.1 数据库设计总览

|---|---|---|
| 系统权限 | sys_role、sys_permission、sys_role_permission、sys_user、staff_schedule、staff_login_log | 角色权限、员工账号、排班、登录日志 |
| 门店 | store、store_payment_setting | 门店信息与支付设置 |
| 客户/会员 | member、member_category、member_address、member_bank_card、member_balance_record、member_points_record、member_recharge_record、red_packet | 会员资产（钱包/积分/红包/银行卡） |
| 菜品 | dish_category、dish_taste、dish_spec、ingredient_category、ingredient、dish、dish_ingredient_rel、dish_review | 菜品档案、原料、评价 |
| 台桌/排队/预约 | table_type、dining_table、queue、reservation | 桌型、台桌、排队、预约 |
| 订单 | cart、orders、order_detail、order_status_log、payment_record、refund | 订单主从、支付、退款、状态日志 |
| 促销 | coupon、member_coupon | 优惠券与用户领用 |
| 库存 | dish_stock、ingredient_stock、stock_check_dish、stock_check_ingredient | 库存与盘点 |
| 硬件/反馈 | printer、receipt_template、feedback | 打印机、小票模板、意见反馈 |

**报表视图（6 个）**：`v_dish_flow` 菜品流水、`v_receipt_report` 收款日报、`v_dish_sales_ranking` 菜品销售排行、`v_store_sales_ranking` 门店销售排行、`v_today_income` 今日收入、`v_refund_record` 退单记录，直接支撑商户端报表模块，避免报表逻辑散落在代码里。

### 7.2 数据设计要点

1. **订单主从**：`orders` + `order_detail` 主从表，明细做名称/价格/规格/口味快照，保证历史订单不受后续改价影响；
2. **金额字段拆分**：订单表拆分菜品合计/优惠/免单/抹零/券/配送/应付/实付，满足报表口径与对账；
3. **状态机留痕**：`order_status_log` 记录订单状态流转，支持业务审计；
4. **会员资产**：余额、积分、红包均设计独立流水表，保证可追溯、可对账；
5. **逻辑外键**：orders.coupon_id 等采用逻辑外键+索引，兼顾性能与一致性；
6. **并发与幂等**：orders.version 乐观锁防状态并发覆盖；payment_record.idempotency_key 幂等键防重复支付回调；
7. **索引覆盖高频查询**：后厨按制作状态（order_detail.status）、收款按日汇总（payment_record.pay_time）、会员流水按来源追溯（member_balance_record.source）等均建对应索引；
8. **演示数据完整**：含 3 门店、9 员工、5 会员、15 菜品、11 台桌、2 订单，以及登录日志/红包/退单等全部核心表演示数据。
